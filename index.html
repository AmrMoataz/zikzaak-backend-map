How to read a requirement.

Every requirement has a stable identifier so a design, a ticket, a test and a table can all point at the same line.

FR-ADM-EVT-011
FR Functional — something the system does.
NFR Non-functional — how well it does it.
Scope which surface it serves.
Area the feature group inside that surface.
Number sequential, never reused.

Scopes

PLATPlatform — API shape, localisation, media, domain events, the module contract
ADMAdmin panel — the only surface that writes catalog data
PUBCustomer — web and mobile app, served by the same endpoints
AGTAgent portal — read-only event search

Areas

API LOC MED EVT CONAPI shape · localisation · media · domain events · contract
CAT VEN MAP TKT PRO AUDcategories · venues · seat maps · ticket categories · promotion · audit
BRW HOM DET SRC DLVbrowse · home · detail · search · delivery and caching
BNDboundaries — what a surface must not be able to do

Non-functional categories

SEC security · PRIV privacy · PERF performance · SCAL scalability · AVAIL availability · OBS observability and audit · COMPAT compatibility · LOC localisation · MAINT maintainability

The three keywords

SHALLMandatory. Not shipping it is a defect.
SHOULDRecommended. Skipping it needs a reason on record.
MAYOptional. Included so the decision is visible, not forgotten.

Traceability

A blue line under a requirement lists the tables and domain types that carry it. Open the requirement to jump to them — and any table or type page shows the requirements it serves, so you can walk it in either direction.

Requirements are indexed by identifier and by full text. Press ⌘K and type FR-ADM-EVT-011, or cache, or fallback.

How to read the access matrix.

Three tables stacked top to bottom. Only the first is real data — the other two are calculated from it. Nothing on this page is typed by hand.

1 · The Final Role Matrix

Nine roles down the side, ten areas of the system across the top. Each cell is a letter saying how much that role may do in that area. This is the only table copied from the client's roles document, and it is what role_permissions is seeded from.

Ffull control — every code in the area
Mmanage — read plus write
Vview — the read codes only
Aapprove — read plus the approve code
Rrequest or escalate — the request code alone, without approve
Oown or assigned cases only — read plus write, unscoped in V1
Nno access

3 · How a score becomes permission codes

Read this one before table 2 — it is the translation key. For each area it lists which permission codes count as read, write, approve and request. A letter in table 1 selects one or more of these columns.

2 · Derived permission grid

Thirty permission codes down the side, the nine roles across the top. Every tick is computed from a letter in table 1 plus the mapping in table 3. A dash means the role does not hold that code.

Working out one role, step by step

1In table 1, find the role's row and read the letter under the area you care about. Operations Manager, Events → M
2Look the letter up above. M means read plus write.
3In table 3, find that area. Events — read is event.view, write is event.create, event.update, inventory.manage.
4Those four codes are the role's permissions for that area. Table 2 shows the same answer as ticks.
5Repeat for the other nine areas and take the union. Add dashboard.view, which every role holds.

That union is the whole permission set for the role. A sensitive code additionally needs an approved grant to hold and recent MFA to use — the red sensitive tag in table 2 marks which.

Reading it the other way — where does a screen get its permission?

Start from the area a screen belongs to, then table 3 gives its codes. The Where the supply modules take their permissions section at the bottom does this for every supply surface, and shows which ones land nowhere.

What the two coloured boxes mean

OrangeA permission code exists but the matrix gives it to nobody — a missing column in table 1.
RedNo permission code exists at all — a missing area. Nothing renders, so the gap is invisible unless flagged.

Two things this page does not tell you

Scope. O and M grant identical codes in V1, because row-level scoping is deferred. Support Agent is indistinguishable from Support Lead on Orders and Support.

Step-up. Holding a sensitive code is not the same as being able to use it. Approval gates the grant; MFA inside a 10-minute window gates each use.
